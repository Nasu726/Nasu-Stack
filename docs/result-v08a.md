## 既存に触ったもの: 1 件（報告）

### `jsonRequest` が成功時の応答を守っていませんでした

```ts
if (res.status === 204) return undefined as T;
return (await res.json()) as T;   // ← ここ
```

これで落ちる場合が 2 つあります。

| 応答 | 起きること |
|---|---|
| 200 だが本文が空 | `res.json()` が落ちる（204 だけ特別扱いしていた） |
| 200 だが HTML | **`SyntaxError: Unexpected token '<'`** がそのまま画面に出る |

2 つ目は、プロキシのエラーページや静的ホスティングの設定ミスでよく起きます。
利用者から見ると「何かの英語が出て送れない」で、原因に辿り着けません。

`content-type` を見て分岐する `readBody()` に置き換えました。
**`submit.ts` の中ではなく `jsonRequest` 本体を直しています。**
`ActionSpec`（`{url, method}` の宣言形）を使う人にも同じ問題が起きるためです。

## 作ったもの

### `createSubmit()` — 5 つだけ引き受ける

`ActionSpec` は「JSON を POST する」だけです。公開フォームでは、
それだけだと必ず次の 5 つにぶつかります。

| | 何が起きるか |
|---|---|
| 1 | 応答が返らない相手 → 永久に「送信中…」 |
| 2 | 通信できない → `Failed to fetch` という英語が画面に出る |
| 3 | 別ドメインへ送る → CORS。**JavaScript からは通信断と区別できない** |
| 4 | 検証エラーの形が API ごとに違う（`errors` / `fields` / `message`） |
| 5 | bot に見つかる。公開フォームは数日で見つかります |

送信そのものは `fetch` のままで、この 5 つだけを足しています。

### 決めたこと 3 つ

**CORS の失敗は通信断と区別できません。** ブラウザは理由を教えてくれないので、

> 送信先に接続できませんでした。通信状況か、送信先の設定（CORS の許可）を確認してください。

と、**両方を含む言い方**にしました。「サーバーが落ちています」と言い切ると、
送信先の設定ミスだったときに利用者を間違った方向へ送ります。

**おとりに引っかかったら、成功したように見せます。** エラーを返すと bot が学習します。

**タイムアウトと「画面から消えた」は同じ `AbortError` ですが、文言を分けます。**
前者は「時間内に応答がありませんでした」、後者は利用者に何も出しません
（利用者の側では何も起きていないので）。

### `HoneypotField` — 人を弾かないおとり

`display: none` では駄目です。有名すぎて、まともな bot は避けます。
かといって普通に置くと人にも見えます。満たすべき条件は 3 つあります。

1. 目に見えない（**消さずに**画面の外へ出す）
2. キーボードで到達できない（`tabIndex={-1}`）
3. 読み上げが読まない（`aria-hidden`）

**2 と 3 を忘れると、目の見えない利用者と Tab で操作する人だけが
この欄を埋めてしまい、送信できなくなります。** おとりで本物の利用者を
弾いては本末転倒なので、実測でも確かめました。

```
✓ Tab で到達できない  (-1)
✓ 読み上げの対象外
✓ 画面の外に出ている（display:none は使わない）
✓ display は none にしない（bot に見抜かれる）  (inline-block)
✓ Tab を 6 回押しても到達しない  (["email","message","","","",""])
```

## 実測 28 件 — 本物の HTTP で

**モックを差し替えるだけでは「本当に飛んだか」が分かりません。**
受け口サーバ（`scripts/_endpoint.mjs`）を立てて、ブラウザから本物の POST を送り、
**受け口が何を受け取ったか**を確かめています。

```
✓ 1. 実際に POST が飛ぶ  (1 件)
✓    送った内容がそのまま届く  ({"name":"なす","message":"こんにちは"})
✓ 2. Content-Type が application/json
✓ 3. おとりに値があると送信しない  (0 件)
✓    それでも成功として扱う（bot に教えない）
✓    おとりの欄は送信先に届けない  ({"name":"人間"})
✓ 4. 422 の {errors:{…}} をフィールドエラーにする
✓ 5. 422 の {fields:{…}} も同じように扱う
✓ 6. 500 + HTML でも SyntaxError が漏れない
✓ 7. 200 + 空の本文を成功として扱う
✓ 8. 200 + HTML でも落ちない
✓ 9. 通信できないとき、英語が出ない
✓    CORS の可能性にも触れる（断定しない）
✓ 10. タイムアウトすると専用の文言になる
✓     「中断しました」とは言わない（原因が違う）
✓ 11. 画面から消えたときは ABORTED になる
✓ 12. 受け口が OPTIONS（プリフライト）に応える  (status 204)
```

## 受け口の見本

`examples/receivers/cloudflare-worker.ts`。1 ファイルで完結し、
サーバーを持たずに済むので静的サイトの構成を崩しません。

**プリフライト（OPTIONS）を最初に処理しています。** ここが抜けると、
ブラウザは本体のリクエストを 1 度も送りません。しかも JavaScript 側からは
「通信できませんでした」としか見えないので、初心者はまず辿り着けません。

README には、必ず踏む 3 つ（プリフライト / `*` のまま公開しない /
サーバー側でも検証する）を書いてあります。

## 送信先の決め方

環境変数で外に出します。**コードに書き込みません。**

```
PUBLIC_CONTACT_ENDPOINT=https://api.example.com/contact
```

未設定のときは送らずに成功したふりをします。開発中に「まだ受け口が無い」だけで
画面が壊れないようにするためです。

`PUBLIC_` で始まる変数だけがブラウザへ渡ります。ここはブラウザから叩く URL なので
それで正しい形ですが、**秘密の鍵は絶対に置かないでください**（誰でも読めます）。
鍵は受け口（Worker）側の秘密として持たせます。
