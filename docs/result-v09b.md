# v0.9b の結果

計画は [plan-v09b.md](plan-v09b.md)、受けた外部レビューは
[review-external-v09a.md](review-external-v09a.md)。

v0.9a を公開したあと、**外部 AI から公開停止（HOLD）を含むレビュー**が届き、
Copilot からも 1 件、作者自身の利用からも 5 件の報告がありました。

---

## 最重要の判定は誤報でした。ただし、その背後の指摘は正しい

レビューの P0（唯一の Blocker）は「scaffold の astro が npm に存在しない」で、
**これは誤りでした。** `astro@7.2.2` は実在し latest でもあり、こちらでは
install → build まで通っています。

問題は、**こちらがそれを機械で否定できなかった**ことです。

手元には node_modules があるので、宣言が間違っていても気づけません。
気づくのは「まっさらな環境の利用者が `npm install` で止まったとき」で、
そのとき利用者は「WebTemplate が壊れている」と判断して離脱します。

> Green CI is not the problem.
> Green CI の意味を広く解釈しすぎることが問題です。

緑の CI が意味していたのは「部品は動く」であって、
**「利用者が始められる」ではありませんでした。**

## Phase A — 二重実行を止めた

配布物の欠陥。**他の何より先に直しました。**

先に赤い判定を作ってから直しています。カタログに「action が何回呼ばれたか」を
画面に出す題材を 2 つ置きました（v0.9a で「検査は通っているが検査対象に
入っていない」を踏んだため）。

### 1. callback が投げると、成功済みの action が retry される

action 本体と `onSuccess` / `onSettled` が同じ `try` の中にありました。
action は成功し、サーバ側の副作用（決済・メール・登録・削除）は**もう
起きている**のに、その後 callback が投げると「action が失敗した」と解釈して
retry します。

**実測: `onSuccess` が投げる + `retry=3` → action が 4 回実行。**

retry の境界を action 本体だけにしました。callback は `callSafely()` で呼び、
例外は console へ出します。状態をエラーにしないのは「action は成功した」のが
事実だからです。嘘の断定をしない代わりに、原因が追える場所には必ず残します。

retry が 0 でも「サーバでは成功しているのに画面はエラー」という食い違いが
残るので、retry の有無に関わらず境界は分ける必要があります。

### 2. 遅い guard を連打すると二重に実行される

`await guard(input)` の**後**に鍵をかけていました。guard が非同期だと、
待っている間に後続の呼び出しが全部その隙間を通り抜けます。

**実測: 150ms 待つ guard を 5 回連打 → action が 5 回実行。**

既存の「5 回連打しても 1 回」の判定は guard の無い経路を見ており、
**この race を見ていませんでした。**

`useResource` にも同じ構造がありました（GET なので実害は小さいものの、
契約として不自然）。同じ方針に揃えています。

## Phase B — 検査の境界を利用者の経路に合わせた

### 生成物を **npm** で検査する

生成物の README も CLI の出力も `npm install` と書いているのに、検査は
pnpm で回していました。**別の道具を確かめても、利用者の経路を確かめたことに
なりません。** 依存の解決も peer の扱いも lockfile の作り方も違います。

`npm install` / `npm run build` に切り替えました。

### 公開の前に、その検査を通す

`pages.yml` は `verify` しか呼んでいませんでした。生成物の install / build /
実ブラウザ / 部品の追加は `verify:create` にしかなく、**リリース判定の外**に
ありました。`verify-create` ジョブを足し、`build` の前提にしています。

そのジョブは **Node 22.12.0**（生成物が要求する下限）で走らせます。
案内より新しい版でだけ通る状態になっていても気づけないためです。

### 宣言した依存が本当に取れるかを見る

`check-scaffold-deps.mjs` が registry へ実際に問い合わせます。
**手元の node_modules を見ません。** わざと `^99.0.0` にして赤くなることを
確認済みです。

これで、**レビュアが誤報した内容を機械で否定できる**状態になりました。

## Phase C — 並列化（280 秒 → 169 秒）

22 工程を直列に回すと待ち時間が長く、長いと「とりあえず push して CI で見る」
ようになります。**それは検査を書いた意味を薄めます。**

依存関係で 3 群に分けました。

| 群 | 中身 |
|---|---|
| 1 | 型検査・ビルド・静的検査・入口の検査（互いに独立） |
| 2 | レジストリ生成 → 依存漏れ・展開・本物の CLI |
| 3 | 実ブラウザ 9 工程（配信済みのサーバを読むだけ） |

**速さのために読みやすさを捨てていません。** 出力は工程ごとに溜めて、
終わった順ではなく定義順に印字します。混ざった出力は読めないので、
速くなっても意味がありません（実測で順序が直列と同じことを確認）。

同時実行数に上限を設けました。実ブラウザの工程はそれぞれ Chromium を立てるので、
無制限に並べると CI の runner（2 コア）では切り替えのほうが重くなります。

## Phase D — 見えるようにした

**カタログもデモサイトも、一度も公開されていませんでした。**
公開されていたのはリンク一覧とレジストリ JSON と tarball だけです。

```
/           入口の案内
/catalog/   38 部品を触って確かめられる
/demo/      実際のサイトがどう見えるか
/r/*.json   レジストリ
```

`apps/site` をカタログ専用のまま置く利点はありませんでした。
検査の題材という役割はそのままで、公開されたデモにもなります。
原本は 1 つで、使い道が 3 つになるだけです。

### サブパス配信の穴を、自分が先に踏む

GitHub Pages の project site は `/WebTemplate/` の下に出ます。`base` を
合わせないと **HTML は取れるのに JS と CSS が 404 になり、真っ白な画面**に
なります。deploy 自体は成功するので、いちばん気づきにくい壊れ方です。

`verify-published.mjs` に判定を足しました。HTML が 200 で返るだけでは
足りないので、**HTML の中から資材の URL を拾って実際に取りに行きます。**

利用者にも同じ問題が出るので、`HowToUse.md` の公開手順を書き直しました
（追加設定の要らない置き場所と、GitHub Pages を分けています）。

## Phase E — 残りの実害と、私が入れた誤り

### 受け口が「届いていないのに成功」を返していた

転送先が未設定のとき `{ ok: true }` を 200 で返していました。
送信した人の画面には「送信しました」と出て、**サイトの持ち主には何も
届きません。** 秘密を 1 つ設定し忘れただけでそうなるので、気づく方法が
ありません。

503 を返します。動作を見たいだけの段階は環境変数で明示的に選ぶ形にしました。
**既定では有効になりません。**

`console.log(input)` もやめました。氏名・メール・本文がそのまま
Cloudflare のログに残ります。設定漏れを直すのに、その中身は要りません。

README には「**CORS は認証でも bot 対策でもない**」を明記しました。
curl も bot もブラウザではないので CORS を見ません。おとりも直接 POST には
効きません。**安全そうに見えて実は効いていない状態が、初心者向けでは
いちばん危ない**ので、この見本に入っていないもの（レート制限・本文の上限）も
書いてあります。

### `.env` が commit されうる状態だった

生成する `.gitignore` に `.env` がありませんでした。**初めての人ほど
`git add .` を打ちます。** 一度 git の履歴に入った鍵は、ファイルを消しても
消えません。作り直しになります。

`.env.example` も生成し、`PUBLIC_` / `VITE_` で始まる値は**ブラウザに
配られる**ので秘密を置かない、と見本の中に書きました。

### Node の版が文書と実装で食い違っていた

astro 7 は `>=22.12.0`、vite 8 は `^20.19.0 || >=22.12.0` を要求するのに、
HowToUse は「Node 18 以上か」と案内していました。「あなたの Node は OK」と
**誤診する**形で、初心者にはいちばん厳しい。

22.12.0 に統一し、CLI は**生成する前に**版を見て止まります。
生成してから `npm install` で EBADENGINE を見せられても、Web が初めての人には
「自分が何か間違えた」としか読めません。

### CLI 自身が危険なコマンドを教えていた

`npx create-webtemplate` は npm で空いている名前です。README は直してあった
のに、`index.mjs` の冒頭コメントとエラーメッセージに残っていました。
**詰まっている人はエラーメッセージを一番信じる**ので、ここが一番危ない。

`check-forbidden.mjs` が機械で見張ります。足した時点で **6 件**見つかりました。

### 検査が避けている危険を利用者に渡していた

生成物の HowToUse は最新版の shadcn をそのまま実行する形でしたが、こちらの
検査は**わざとそれを避けて**固定版を使っています。確かめた版を利用者にも
使ってもらう形にしました。

### 文書のトークンが実装に無かった

HowToUse に `3xs` と書きましたが実在しません（実体は `none`）。
v0.9a で私が入れた誤りです。**エラーにならないので切り分けにくい種類**で、
初心者は「書いたのに効かない」を踏みます。`tokens.css` から読む形にし、
一致を判定にしました。

### 壊れた URL でサーバが落ちる（Copilot）

`_static.mjs` の `decodeURIComponent` が try の外にありました。壊れた
percent-encoding が 1 回来るとプロセスごと落ちます。400 を返します。
