# 方向性まとめ（追記版）

元のまとめに、実装して分かったことと調査で裏が取れたことを足しました。
**追記** と書いてある箇所が今回足した部分です。相違点は隠さず書いています。

---

## 1. 最終的な目標

初心者でもスムーズに開発を始められる「親切さ」を持ちつつ、Wix や Elementor よりも
**自由度の高い開発体験**を提供するテンプレート（またはテンプレート生成・編集ツール）を作ること。

単なる静的サイトの雛型ではなく、配置やレイアウトの調整がしやすい形で、
最終的には普通のコードとして扱えるものを目指す。

> **追記 — 「親切さ」を 2 本の柱に分ける**
>
> 現状この 1 語に、性質のまったく違う 2 つの困りごとが混ざっています。
>
> | | 困りごと | いつ詰まるか |
> |---|---|---|
> | **A. 配置の親切さ** | 幅・余白・並びが決められない | 作り始めた直後 |
> | **B. 挙動の親切さ** | 押した後・送った後・失敗した時が書けない | 見た目ができた後 |
>
> A は「動かないが見える」段階、B は「見えるが動かない」段階の問題です。
> 初心者は **両方で必ず詰まる**ので、どちらか片方だけでは「サイトが作れる」に届きません。
> v0.1 で先に B を作ったのは、A より競合が薄く、かつ A の土台になるからです（後述）。

---

## 2. ターゲット

- 主なターゲット：プログラミング初心者〜中級者
- 副次的なターゲット：自由度を求める開発者
- Wix や Elementor では物足りないが、ゼロからコードを書くのはハードルが高い人

> **追記 — 「コードを全く書けない人」を含めるかは、今すぐ決めるべき分岐点**
>
> ここが曖昧なままだと、この先の全部の判断がぶれます。
>
> - **含める** → ビジュアルエディタが必須になる。コードを一度も見ないで完成まで行ける必要があるため。開発規模が一桁変わる
> - **含めない**（＝「少しは触れる」を下限にする） → 制約されたレイアウト部品で足りる。ビジュアルエディタは任意の後付けになる
>
> **含めないことを勧めます。** 理由は 3 節に書きます。
> 「コードを全く書けない人」向けの入口は、既に v0 / Lovable / Base44 が
> 自然言語で提供していて、そこと同じ土俵に乗るのは現実的ではありません。

## 3. 既存ツール・フレームワークとの差異

| 比較対象 | 既存の特徴 | 目指す差異 |
|---|---|---|
| **Wix / Elementor** | ビジュアル操作が強力で初心者に優しいが、自由度が低く、コードの質や拡張性に限界がある | ビジュアル操作の親切さを残しつつ、**きれいなコードとして出力・編集可能**にして自由度を上げる |
| **Better-T-Stack / T3 Stack** | 型安全で柔軟なフルスタック土台は優秀だが、UI・レイアウトはほぼ自分で作る必要があり、初心者には不親切 | UI 部品やレイアウト調整を最初からサポートし、初心者でも配置に苦しまないようにする |
| **Astro / Next.js などの純粋なフレームワーク** | 自由度は高いが、初心者にはセットアップやレイアウト調整が難しい | テンプレート＋補助で「最初のハードル」を下げる |
| **完全なノーコードツール** | 簡単だがロックインが強い | 最終的に普通のコードプロジェクトとして扱えるようにする |

> **追記 — この表に、直接の競合が 3 行抜けています**

| 比較対象 | 実態（2026 年時点の調査） | どう扱うべきか |
|---|---|---|
| **Builder.io / Plasmic / Makeswift** | 「ビジュアル編集 → きれいなコード」を既にやっている。特に Plasmic は React コード生成に振り切っている。**ただし 3 つとも、ページ内容は独自のクラウド形式に保存され、セルフホストの選択肢が無い**。移行するには内容を書き出すか、静的コードとして作り直す必要がある | **正面から競合。しかも「ロックインしない」という要件を、この 3 つは満たせていない** — そこが唯一の勝ち筋 |
| **v0 / Lovable** | 自然言語 → Next.js + shadcn/ui + Tailwind のコード。「初心者が配置に苦しまない」への現代的な回答はここ | ここが「コードを書けない人」の入口を既に埋めている。同じ土俵に乗らない |
| **shadcn ブロック市場**（Shadcnblocks / Shadcn Studio / Tailark 等） | ランディング・料金表・ヒーロー等のセクションが計 2,500 個以上、$149〜399 で流通。**全て見た目だけ（presentational）** | 「4. ページ・セクションのテンプレート」は**既に飽和**。ここを自作するのは労力の無駄 |

> **重要な発見**: Plasmic の週間ダウンロードは約 1 万、Builder.io が約 4 万、Makeswift が約 5 千。
> 「Wix の代替」と呼べる規模ではありません。
> つまり **「ビジュアル編集 → きれいなコード」という筋自体は、10 年近く挑戦されて、まだ誰も広く勝てていない**。
> 難しいから避けろ、ではなく、**そこに賭けるなら他を全部捨てる覚悟が要る**という意味です。

## 4. 最低限欲しい機能

- 事前に用意されたページ・セクションのテンプレート（ランディング、ブログ、会社サイトなど）
- よく使う UI 部品（ボタン、テキストボックス、カード、フォームなど）が最初から揃っている
- **レイアウト調整のサポート**
  - グリッド表示やガイド
  - 要素の幅・余白・配置の視覚的な調整
  - 可能であればコンポーネントや div 内部での相対位置の決定支援
- 静的サイトを中心に、汎用的な動的ページの雛型も扱える
- 生成・編集した結果がきれいなコードとして残る

> **追記 — 「UI 部品」を 2 種類に割る必要があります**
>
> 「ボタン、テキストボックス、カード、フォーム」と並べると同じ粒に見えますが、
> **カードは見た目だけで完成、フォームは動かないと意味が無い**。ここは別物です。
>
> - **見た目で完成するもの**（カード、ヒーロー、料金表）→ 既に 2,500 個流通している。**作らない**
> - **動かないと意味が無いもの**（フォーム、リスト、アップロード、ボタン）→ **誰も作っていない**。v0.1 でここを押さえた
>
> v0.1 の `AsyncForm` は「送信関数を 1 つ渡すと、送信中・成功・失敗・
> フィールド単位のエラー表示・二重送信の防止まで全部入る」ものです。
> このまとめの「フォーム」が見た目のフォームを指しているなら、期待値が 1 段低いです。

> **追記 — 「レイアウト調整のサポート」の中身を、ビジュアル操作から先に切り離す**
>
> ここが今回いちばん言いたい点です。次の 5 節に書きます。

## 5. 満たすべき要件

- **初心者への親切さ**：配置や幅決めに苦しまず、並べたり調整したりするだけで最低限のサイトが作れる
- **自由度の高さ**：後から普通のコードとして深く編集・拡張できる。特定のプラットフォームに強くロックインしない
- **実用性**：静的サイトや比較的汎用的な動的ページを対象に、実際に使える品質のものを提供する
- **開発体験のバランス**：ビジュアル操作の利点を取り入れつつ、コードの透明性・編集性を損なわない

> ### 追記 — 「配置で苦しむ」原因の見立てが、たぶん一段ずれています
>
> まとめでは「自由度が高すぎて難しい」→「ビジュアル操作で楽にする」という流れになっています。
> しかし実際の原因は **自由度ではなく、選択肢が無限にあること**です。
>
> 余白を決めるとき、初心者は `8px` と `12px` のどちらが正しいか判断できません。
> ビジュアルエディタでドラッグしても、**選択肢が無限であることは変わらない**ので、
> 判断できないままです。Wix で作ったサイトが整って見えないのはこれが理由です。
>
> 効くのは操作方法を変えることではなく、**選べる値を減らすこと**。
> この方向には確立した先例があります。SEEK 社の Braid Design System は、
> 明確な原則を 1 つ置いています。
>
> > **コンポーネントは自分の周囲の余白を持たない。余白は全てレイアウトコンポーネントが所有する。**
>
> そのうえで `Stack`（縦の間隔）/ `Inline`（横に並べて折り返す）/ `Columns`（段組と折り畳み）/
> `Tiles`（等間隔グリッド）/ `ContentBlock`・`PageBlock`（最大幅）だけを提供し、
> **任意の余白の決定を排除**しています。
>
> ```tsx
> // 余白の値を考える余地が無い。space は決まった段階からしか選べない
> <PageBlock>
>   <Stack space="large">
>     <Hero />
>     <Columns space="medium" collapseBelow="tablet">
>       <Card /> <Card /> <Card />
>     </Columns>
>   </Stack>
> </PageBlock>
> ```
>
> **これはコードのままで実現でき、ビジュアルエディタより桁違いに安い。**
> しかも生成物は最初からきれいなコードなので、「出力の品質」を後から作り込む必要がありません。
>
> ビジュアルエディタを否定しているのではなく、**順番の話**です。
> 制約されたレイアウト部品が無い状態でビジュアルエディタを作ると、
> エディタは無限の CSS 値を吐くので、結局「きれいなコード」になりません。
> **先に制約を作り、その上にエディタを載せる**なら、エディタは
> 「限られた選択肢から選ぶ UI」になって実装量も激減します。

## 6. 自由度の位置づけ

- Wix / Elementor より明らかに高くする（コード出力・直接編集が可能）
- 純粋なフレームワーク（Astro / Next.js 単体）よりは低くても良いが、できるだけ近づけたい
- 「最初はビジュアルで楽に作り、慣れたらコードで自由に触る」という段階的な自由度を重視

> **追記 — 「段階的な自由度」は設計原則として明文化しておく価値があります**
>
> v0.1 では **エスケープハッチを必ず 1 段下に置く**という形で既に実装しています。
>
> ```
> <ActionButton action={...}>   ← 何も考えなくていい層
>       ↓ 物足りなくなったら
> <Button onClick={...}> + useAction()   ← 状態だけ借りる層
>       ↓ さらに物足りなくなったら
> useState / fetch                        ← 素の React
> ```
>
> どの層で止まっても壊れません。レイアウトも同じ構造にすべきです。
>
> ```
> <Stack space="large">      ← 決まった値から選ぶだけ
>       ↓
> <Box padding={...}>        ← もう少し細かく
>       ↓
> className="..."            ← 素の Tailwind
> ```
>
> **「乗り換え」ではなく「降りる」形にすること。**
> Wix が嫌われるのは、降りようとすると全部作り直しになるからです。

## 7. 現状の認識

- デザイン・UI・レイアウト調整が一番のボトルネック
- 部品を「並べて繋ぐ」だけである程度動く状態が理想
- 完全にすべてを自動化するのは現実的でない
- ビジュアル操作（または強力なグリッド・相対位置サポート）が体験を大きく改善する

> **追記 — 「並べて繋ぐ」の「繋ぐ」側が v0.1 で片付いています**
>
> 「並べて繋ぐ」は実は 2 つの動詞です。
>
> - **並べる** = レイアウト。→ **未着手**。5 節の制約プリミティブが答え
> - **繋ぐ** = 部品と処理の接続。→ **v0.1 で完了**
>
> 「繋ぐ」側は `Action` 契約 1 本に集約済みです。
>
> ```ts
> (input, ctx) => Promise<output>
> ```
>
> 利用者はこの形の関数を書くだけで、読込中・成功・失敗・空・二重送信・中断が全部付いてきます。
> Astro の island へは関数を渡せないので、`{ url, method }` という
> **JSON で書ける形**も同じ口で受けられるようにしてあります。
> これは「コードを書かない人向けの入口」への布石でもあります
> — ビジュアルエディタを作るなら、エディタが吐くのはこの JSON になります。

## 9.【追記】優先順位の提案

全部やると年単位です。効果 ÷ コストで並べ替えると次になります。

### 最優先 — レイアウト・プリミティブ（v0.2）
`PageBlock` / `ContentBlock` / `Stack` / `Inline` / `Columns` / `Tiles` / `Box`。
**「配置で苦しむ」への最短の答えで、実装は 1 週間規模。**
先例（Braid）があるので設計を発明する必要がない。
これが無いとビジュアルエディタも作れないので、いずれにせよ通る道。

### 次 — 状態を持つ部品を増やす（v0.2 後半）
`AsyncSelect` / `FileDrop` / `DataTable` / `Toast` / `ConfirmDialog`。
既存市場に無いものだけを増やす。見た目だけの部品は作らない。

### その次 — テンプレート化（v0.3）
レイアウト部品が揃って初めて、ランディング／ブログ／会社サイトの雛型が
「組み合わせ」として安く作れるようになる。順番を逆にすると全部手書きになる。

### 判断保留 — ビジュアル編集（v0.4 以降）
上記が揃った後なら「限られた選択肢から選ぶ UI」で済むので現実的になる。
先に作ると必ず破綻する。

### 判断保留 — 認証・課金の配線
有償ボイラープレートが $200〜600 取っている領域。
アダプタ方式にすればバックエンドに依存せず作れる。ただし静的サイト中心の
方針と直交するので、ターゲットを固めてから。

## 10.【追記】次に決めるべきこと（3 つだけ）

1. **「コードを全く書けない人」を対象に含めるか**
   含めるならビジュアルエディタが必須になり、規模が一桁変わる。**含めないことを推奨**

2. **レイアウト・プリミティブを v0.2 の最優先にしてよいか**
   これが「配置のボトルネック」への実際の答えだと考えている

3. **`ActionProvider`（アプリ全体の既定エラー処理）を入れるか**
   前回からの持ち越し。入れると `onError` を毎回書かずに済むが、暗黙の挙動が増える。
   Toast と同時に判断するのが自然
