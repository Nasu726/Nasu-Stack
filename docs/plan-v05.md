## 1. DataTable の行選択

### 決めること：「全選択」は何を選ぶのか

ここが v0.4 で先送りにした論点です。意味が 3 通りあります。

| | 意味 | 実装 |
|---|---|---|
| (1) | **いま表示している行だけ** | `Set<Key>` に現ページ分を足す |
| (2) | 取得済みの全行 | 同上（クライアント側なら (1) と同じ） |
| (3) | サーバー上の全件（条件に一致するもの全部） | ID の集合ではなく**条件**を持つことになる |

**(3) は根本的にデータ構造が違います。** 1,234 件のうち 50 件だけ画面にあるとき、
「全部選択」を ID の集合で表すのは不可能です（残り 1,184 件の ID を知らないため）。
Gmail が「50 件を選択しました。条件に一致する 1,234 件すべてを選択」という
別リンクを出しているのはこのためです。

**決定案：**

- 選択は **`Set<Key>` で保持し、ページを移っても残す**
- ヘッダのチェックボックスは **「いま表示している行」だけ**を対象にする
- 他のページの分も含めた合計を「N 件選択中」と表示し、「全解除」を出す
- **(3) は範囲外。** サーバー側の一括操作は別の設計が要るので、今回は作りません

### 危ないところ

> **`indeterminate` は属性ではありません。**
> 「ページ内が一部だけ選択されている」状態を示す `indeterminate` は
> HTML 属性ではなく DOM のプロパティです。JSX に書いても効きません。
> `ref` 経由で `el.indeterminate = true` と代入する必要があります。
> **確実に踏む罠なので先に書いておきます。**

> **`getKey` が必須になります。**
> 現在 `getKey` は任意で、省略すると配列の index を使います。
> 選択を index で持つと、**並べ替えた瞬間に選択が別の行へずれます。**
> 選択を有効にしたら `getKey` を必須にします（型で強制できないので実行時に警告）。

> **行クリックとチェックボックスの競合。**
> チェックボックスのクリックが `onRowClick` へ伝播すると、
> 選択と同時に詳細が開きます。`stopPropagation` が要ります。

> **選択したまま並べ替え・ページ移動したときに「消えた」と誤解される。**
> キーで保持していれば残りますが、画面に出さないと分かりません。
> 「N 件選択中」を常に出します。

> **Shift+クリックの範囲選択。**
> 表では期待される操作ですが、基準点（最後に触った行）の管理が要ります。
> 並べ替えやページ移動をまたぐと基準点が無意味になるので、そのとき破棄します。

> **カード表示でのチェックボックス。**
> 狭い画面ではカードなので、置き場所が変わります。カード先頭に置きます。

## 2. useOptimisticList — ここが今回いちばん危ない

「追加・削除・更新を、サーバーの応答を待たずに画面へ反映し、失敗したら戻す」フックです。

### 素朴な作り方は必ず壊れます

よくある実装はこうです。

```ts
const snapshot = items;        // 今の配列を控える
setItems(next);                // 楽観的に反映
try { await save(); }
catch { setItems(snapshot); }  // 失敗したら控えに戻す ← これが壊れる
```

**壊れる筋書き:**

```
1. A を追加  → 画面に A が出る（サーバー応答待ち）
2. B を削除  → 画面から B が消える（別のリクエスト）
3. 1 が失敗  → snapshot に戻す
   → A が消えるのは正しい。**しかし B が復活する。**
      snapshot は 2 より前の状態だからです。
```

操作が 1 つずつ順番に終わる前提の実装なので、
**同時に走ると他の操作を巻き戻します。**

### 正しい構造：基準 + 保留中の差分

```
表示される配列 = 基準の配列 に 保留中の操作を順に適用したもの

  base:    サーバーから取得した確定状態
  pending: [{ id, kind: "add"|"remove"|"update", ... }]

  成功 → その操作を pending から外し、base を更新
  失敗 → **その操作だけ** pending から外す（他は残る）
```

これなら操作が何本同時に走っても、失敗した 1 本だけが消えます。

### API

```tsx
const list = useOptimisticList({
  load: (_, ctx) => jsonRequest<Task[]>("/api/tasks", { ctx }),
  getKey: (t) => t.id,
});

// 追加。第 2 引数がサーバーへ送る関数
list.add({ title: "新しい仕事" }, (item, ctx) => api.create(item, ctx));
list.remove(task, (item, ctx) => api.remove(item.id, ctx));
list.update(task, { done: true }, (item, ctx) => api.update(item, ctx));

list.items      // 基準 + 保留中を反映した配列
list.pendingOf(key)  // その行が保留中か（薄く表示するなど）
```

### 危ないところ

> **追加した項目にはまだサーバーの ID がありません。**
> 仮のキーを振り、成功したらサーバーが返した本物と差し替えます。
> **その差し替えの前に「削除」されたら**、仮キーで削除要求を送ることになります。
> → 保留中の追加が完了するまで、その行の削除は待たせます（または禁止）。

> **失敗して行が戻ったことに気づかれない。**
> 画面から消えた／復活したことを通知しないと、利用者は保存されたと思い込みます。
> `ActionProvider` の通知へ流します（画面内に出せていないので、
> v0.2 で決めた規則に照らして通知するのが正しい場面です）。

> **`load` で再取得したとき、保留中の操作が消える。**
> 再取得は `base` を差し替えるだけにし、`pending` は残します。

> **同じ行を続けて 2 回更新したとき。**
> 後の更新が先に届くと、古い値で上書きされます。
> 同一キーの update は直列化します（前のが終わるまで待つ）。

## 3. 入力部品

### まず、既存のバグを直します

**`AsyncForm` は複数値を取りこぼします。**

```ts
// 現在の実装
const fd = new FormData(e.currentTarget);
void state.run(Object.fromEntries(fd.entries()));
```

`Object.fromEntries` は**同じキーが複数あると最後だけ残します。**
つまり次が壊れます。

- `<select multiple>` で 3 つ選んでも、1 つしか送られない
- 同じ `name` のチェックボックスを複数置くと、1 つしか送られない

さらに **未チェックのチェックボックスは FormData に現れません。**
`false` ではなく「キーごと無い」状態になるので、
受け取り側が `values.agree === false` を期待していると必ず外れます。

**直し方**: `fd.entries()` を手で畳み、同じキーが複数あれば配列にします。
チェックボックスは `<input type="hidden" value="">` を前に置いて、
未チェックでも空文字が届くようにします。

これは**入力部品を作る前に直さないと、作ったそばから壊れます。**

### 作るもの

`Field` に `type` を足すのではなく、**別コンポーネントにします。**
`options` が要る・値の型が違う・ラベルの付き方が違うためです。

```tsx
<SelectField name="team" label="チーム" options={[...]} />
<CheckboxField name="agree" label="規約に同意する" />
<CheckboxGroup name="tags" label="タグ" options={[...]} />
<RadioGroup name="plan" label="プラン" options={[...]} />
<DateField name="due" label="期限" />
```

### 危ないところ

> **チェックボックスとラジオのタップ領域。**
> `tokens.css` の `pointer: coarse` ルールは
> `:not([type=checkbox]):not([type=radio])` で除外しています。
> 四角自体は 16px 程度なので、**ラベル全体を当たり判定にします。**
> `pnpm check` の「タップ領域 24px 未満」に引っかかるはずなので、
> そこが安全網になります。

> **`<input type="date">` は 16px 未満だと iOS が拡大します。**
> `Field` で踏んだのと同じ罠。日付入力も例外ではありません。

> **`RadioGroup` は `fieldset` + `legend` が要ります。**
> `<label>` を並べるだけだと、スクリーンリーダーが
> 「何についての選択肢か」を読めません。

> **`DateField` に自前カレンダーは作りません。**
> ブラウザ標準を使います。見た目の差は出ますが、
> 自前だと日本語入力・キーボード操作・タイムゾーンで
> 部品 1 個ぶんの規模になります。今回の範囲を超えます。

## 4. 実測で確かめる項目

先に列挙しておきます。

| # | 確かめること | 落ちたらどうするか |
|---|---|---|
| 1 | `indeterminate` が実際に付くか（属性ではないので ref 経由） | ref 代入に直す |
| 2 | ページを移っても選択が残り、「N 件選択中」が正しいか | Set の持ち方を直す |
| 3 | チェックボックスのクリックで `onRowClick` が発火しないか | stopPropagation |
| 4 | 並べ替えても選択が同じ行に付いているか | `getKey` 必須の徹底 |
| 5 | Shift+クリックで範囲が選べるか | 基準点の管理を直す |
| 6 | **追加が失敗したとき、同時に走った削除が復活しないか** | 差分の持ち方を直す |
| 7 | 同じ行を 2 連続で更新して、古い値が勝たないか | 同一キーの直列化 |
| 8 | 再取得しても保留中の操作が消えないか | base だけ差し替える |
| 9 | `<select multiple>` で複数値が送られるか | FormData の畳み方を直す |
| 10 | 未チェックのチェックボックスが値として届くか | hidden を置く |
| 11 | チェックボックス／ラジオのタップ領域が 24px 以上か | ラベルを当たり判定に |
| 12 | 日付入力の font-size が 16px 以上か | 直す |
| 13 | `RadioGroup` が `fieldset`/`legend`/`role` を持つか | 直す |
| 14 | 新部品が `pnpm check` を全幅で通るか | 直す |
