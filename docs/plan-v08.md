# v0.8 前半 計画 — フォームの送信先を配線する

## なぜここか

最初に立てた目標（1 通目）にこう書いてありました。

> ボタンなどのコンポーネントは呼び出す関数を OnCall にセットするだけで良いようにすれば
> API 対応もできます。**予め関数を用意しておいて「これを呼び出してね」と決めておく**
> ことで初心者でもスムーズな開発を促します。

**この「予め用意しておく関数」が、まだ 1 つもありません。**
`/contact/` のフォームは偽の API を呼んでいて、利用者が最後に必ずぶつかるのは
「で、どこに送るの？」です。

---

## 現状の穴（コードを読んで確認）

| 場所 | 何が起きるか |
|---|---|
| `jsonRequest` の成功時 `res.json()` | 200 なのに HTML が返ると **`SyntaxError: Unexpected token '<'`** がそのまま画面に出る。プロキシのエラーページや、設定ミスの静的ホスティングでよく起きます |
| 同上、200 で本文が空 | `res.json()` が落ちる（204 だけ特別扱いしています） |
| `toActionError` の通信断 | `fetch` は `TypeError: Failed to fetch` を投げます。displayMessage が**英語のまま**利用者に出ます |
| どこにも無い | タイムアウト。応答が返らない相手だと永久に「送信中…」 |
| どこにも無い | CORS。静的サイトから別ドメインへ送る構成では**必ず**踏みます |
| どこにも無い | スパム対策。公開フォームは数日で bot に見つかります |

最後の 2 つは「初心者が自力で解決できない」類です。エラーの見え方が
「通信に失敗しました」としか出ないので、**原因に辿り着けません。**

## 作るもの

### 1. `lib/submit.ts`（純粋・フレームワーク非依存）

```ts
const submit = createSubmit({
  url: "https://api.example.com/contact",
  timeout: 15000,
  honeypot: "company",   // この名前の欄に値が入っていたら送らない
});

<AsyncForm action={submit} />
```

引き受けるもの:

- **タイムアウト**（既定 15 秒）。`ctx.signal` と合成するので、
  アンマウントでの中断とタイムアウトが両立します
- **失敗の翻訳**。通信断 / CORS / タイムアウト / HTML が返った、を
  それぞれ**日本語で、次にやることが分かる文**にします
- **422 の吸収**。`{errors:{field:msg}}` でも `{fields:{...}}` でも
  `AsyncForm` のフィールドエラーに繋ぎます
- **honeypot**。値が入っていたら送信せず、**成功したように見せます**
  （bot に「弾かれた」と教えると学習されるため）

### 2. `jsonRequest` を堅くする（**既存ファイルの変更 1 件・報告対象**）

成功時の `res.json()` を守り、`content-type` を見て分岐します。
これは `submit.ts` だけの問題ではなく、`ActionSpec` を使う全員に効くためです。

### 3. `HoneypotField`（新規ファイル）

`display:none` では bot に見抜かれます。画面外へ出し、`tabindex="-1"`、
`autocomplete="off"`、`aria-hidden` を付けます。**人には見えず、
キーボードでも辿り着かず、読み上げも読まない**必要があります。

### 4. 受け口の見本（`examples/receivers/`）

Cloudflare Worker の骨格。**CORS のプリフライトを含めます。**
ここが抜けると、ブラウザは本体のリクエストを送る前に諦めます。

### 5. 検証用の受け口サーバ（`scripts/_endpoint.mjs`）

**実際に POST を受けるサーバを立てて測ります。** モックを差し替えるだけでは
「本当に飛んだか」が分かりません。

## 気をつけるところ（先に挙げておく）

- **CORS の失敗は、JavaScript からは通信断と区別できません。**
  `fetch` は理由を教えてくれません。だから文言は
  「通信できませんでした（相手先の設定かもしれません）」のように、
  **両方を含む言い方**にする必要があります。嘘の断定をしないこと
- **honeypot で弾いたとき、成功を装う。** エラーを返すと bot が学習します
- **タイムアウトの中断と、アンマウントの中断を混ぜない。**
  どちらも AbortError ですが、利用者に見せる文言は別です
  （前者は「時間がかかりすぎました」、後者は何も出さない）
- **`AbortSignal.any` は新しめの API です。** 使えない環境向けに
  手で合成する必要があるか、実測で確かめます
- **送信内容に honeypot の欄を混ぜない。** 受け口に余計なキーが届きます
- **成功したのに本文が空**は正常です（204 も 200 も）。落とさないこと

## 実測で確かめる項目

1. 実際に POST が飛び、受け口が受け取った JSON が送信内容と一致する
2. `Content-Type: application/json` が付いている
3. honeypot に値を入れると**受け口にリクエストが届かない**のに、成功表示になる
4. 422 + `{errors:{name:"…"}}` → その欄の下にエラーが出る
5. 422 + `{fields:{…}}` でも同じ
6. 500 + HTML 本文 → 日本語のメッセージ。`SyntaxError` が漏れない
7. 200 + 空の本文 → 成功として扱う
8. 200 + HTML 本文 → 落ちない
9. 通信断 → 日本語のメッセージ（英語の `Failed to fetch` が出ない）
10. タイムアウト（テストでは 300ms に設定）→ 専用の文言
11. 送信中にアンマウント → 中断される。**エラーは表示しない**
12. 二重送信の防止が、実際の HTTP でも効く（受け口が受けたのは 1 回）
13. `HoneypotField` が Tab で到達できない・読み上げ対象外
14. 受け口サンプルの OPTIONS（プリフライト）が正しく応答する
15. 既存の判定 214 件が緑のまま
