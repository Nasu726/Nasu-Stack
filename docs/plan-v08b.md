# v0.8 後半 計画 — 入口をつくる

## いま何が壁になっているか

部品は 38 個、判定は 242 件あります。しかし**始められません。**

```
npx shadcn add @nasu/async-form
```

これが動くには、利用者が**先に**次を全部用意している必要があります。

- Vite か Astro のプロジェクト
- Tailwind v4 と `@tailwindcss/vite`
- `tsconfig.json` の `paths`（`@/*` → `src/*`）
- `tokens.css` / `themes.css` の読み込み
- React と TypeScript の設定

**「誰でも簡単に Web サイトが作れる」という最初の目標に対して、
ここが最大の穴です。** 部品をいくら増やしても、入口が無ければ届きません。

## いちばん怖いところ: 部品が 2 か所になる

生成用のテンプレートに部品をコピーして持つと、
**`registry/nasu` と合わせて同じファイルが 2 か所**になります。

これはこのリポジトリが何度も踏んだ失敗そのものです。

- ヘッダの高さが 2 か所 → アンカーが壊れた
- タブの一覧が 3 か所 → 新しい画面が検査から漏れた
- 下書きの除外が 3 か所 → 漏れたら気づけない
- 入力欄の class が 4 か所 → テーマを変えると 1 つだけ違う見た目に

**同じ轍を踏まない作りにします。**

```
registry/nasu/            ← 唯一の原本
        ↓  scripts/build-create-template.mjs（生成）
packages/create-webtemplate/template/   ← .gitignore。commit しない
```

テンプレートは**必ず生成物**にして、リポジトリには置きません。
手で編集する余地を無くせば、ずれようがありません。

## 気をつけるところ（先に挙げておく）

- **既存のディレクトリを上書きしない。** 空でなければ止めます。
  `create` 系のツールで一番やってはいけない事故です
- **プロジェクト名を検証する。** 空白・大文字・`/`・先頭の `.` は
  `package.json` の `name` として不正です。弾くか直すかを決める
- **TTY でないときも動く。** CI や `--yes` で対話なしに通ること
- **`tsconfig` の `paths` は registry の `target` と一致させる。**
  ここがずれると、生成直後は動くのに `shadcn add` で足した部品が壊れます
- **Tailwind v4 の `@source`。** レジストリのソースは走査対象の外に置かれることが
  あるので、生成先で正しいパスになっているか実測が要ります
- **パスをシェルに出さない。** `path.join` だけで組み立てます（Windows 対策）
- **生成物に `node_modules` を作らない。** 入れるかどうかは利用者に選ばせます

## 実測で確かめる項目

**「生成できた」では足りません。生成物が本当に動くかを測ります。**

1. `create my-site --template astro --yes` が成功する
2. `--template vite --yes` も成功する
3. 生成されたファイルの一覧が期待どおり
4. **既存の空でないディレクトリには生成しない**（上書き事故の防止）
5. 空のディレクトリになら生成できる
6. おかしなプロジェクト名を弾く（空白 / 大文字 / 先頭の `.`）
7. `tsconfig.json` の `paths` が registry の `target` と一致している
8. 生成物で `pnpm install` が通る
9. 生成物で **型検査が通る**
10. 生成物で **ビルドが通る**
11. ビルドした生成物を配信して、**実ブラウザで画面が出る**
12. その画面が**端末幅の検査（5 幅）を通る**
13. テンプレートが原本と同期している（生成し直して差分ゼロ）
14. 既存の 242 件が緑のまま

8〜12 は時間がかかるので、`pnpm verify` とは別のコマンド
（`pnpm verify:create`）にします。**ただし手動ではなく機械で回します。**

5. 生成物を実際に install → build → 配信して 8〜12
6. `pnpm verify` → docs
